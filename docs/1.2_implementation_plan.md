# Dali QR 1.2 — Implementation Plan

**Status:** Core implementation complete; format/device QA pending
**Target release:** 1.2
**Requirements:** [Version 1.2 Improvements](next_version_improvements.md)
**Platforms:** iOS and Android
**Plan date:** 2026-09-13

---

## 1. Outcome

Version 1.2 will:

1. Rename the user-facing application from **Dali Secure QR** to **Dali QR**.
2. Continue scanning QR Code and add UPC-A, UPC-E, EAN-8, EAN-13, Code 128,
   Code 39, Code 93, Codabar, and ITF-14.
3. Decode those formats from the live camera, photo library, and images shared
   from other applications.
4. Show the format and decoded contents inside Dali before offering any
   contextual action.
5. Preserve existing user data, saved items, settings, purchase entitlement,
   package identity, and Secure QR verification behavior.

Barcode generation, product lookup, inventory mode, multiple-image shares,
PDF input, and additional 2D formats are not part of 1.2.

## 2. Implementation principles

- Use one domain model and one result flow for camera, gallery, and shared
  images.
- Keep plugin types at the scanner boundary; do not persist
  `mobile_scanner` enum indexes.
- Persist format names as stable strings so a dependency update cannot corrupt
  history meaning.
- Append new values to any existing persisted Dart enum; never reorder its
  values.
- Apply Secure QR comparison-code calculation only to QR Code results.
- Treat decoded content as inert and untrusted until the user selects a
  labeled action.
- Do not render a scanned 1D barcode as a QR image in history or Saved.
- Enable an explicit, tested format allowlist rather than
  `BarcodeFormat.all`.

## 3. Target architecture

### 3.1 Domain model

Add `lib/features/scan/domain/scanned_code.dart` with a package-independent
model similar to:

```dart
enum ScannedCodeFormat {
  qrCode,
  upcA,
  upcE,
  ean8,
  ean13,
  code128,
  code39,
  code93,
  codabar,
  itf14,
}

enum ScanSource { camera, gallery, sharedImage }

final class ScannedCode {
  const ScannedCode({
    required this.value,
    required this.format,
    required this.source,
    this.rawBytes,
  });

  final String value;
  final ScannedCodeFormat format;
  final ScanSource source;
  final Uint8List? rawBytes;
}
```

Provide stable storage keys and human-readable labels with exhaustive switches.
Storage decoding must fall back safely to QR for migrated records and reject or
label unknown future values without crashing.

### 3.2 Scanner adapter

Add a scanner-boundary adapter, for example
`lib/features/scan/data/mobile_scanner_code_adapter.dart`, responsible for:

- the explicit `BarcodeFormat` allowlist;
- mapping plugin formats to `ScannedCodeFormat`;
- discarding unknown, unsupported, null, and empty results;
- trimming neither whitespace nor leading zeroes from decoded values;
- deduplicating identical `(format, value)` results; and
- returning results in a deterministic order.

Keep raw values exact. In particular, do not remove the leading zero when a
platform reports UPC-A as EAN-13. Add a presentation-only note for this known
platform difference if device tests demonstrate it. Do not silently mutate the
identifier in 1.2.

For still images, return all unique results. For live camera scanning, select
the first result according to the adapter's documented format-priority order,
pause the scanner, and open the result.

### 3.3 Presentation state

Refactor `QrScannerPage` state from `_decodedText` to either:

- no result;
- one `ScannedCode`; or
- a non-empty list of `ScannedCode` results awaiting user selection.

Keep payload classification separate from symbol format. A Code 128 containing
a URL may be classified as a URL, but its symbol remains Code 128 and it does
not receive Secure QR verification.

## 4. Work packages

### WP1 — Format support spike and fixtures

**Purpose:** Confirm the required format set before changing persistence or UI.

Tasks:

1. Create independently generated PNG fixtures for every required symbology,
   including short and long valid examples.
2. Include paired UPC-A and zero-prefixed EAN-13 fixtures to document native
   reporting behavior.
3. Exercise `mobile_scanner` 7.4.0 `analyzeImage` on current minimum-supported
   iOS and Android versions and at least one physical device per platform.
4. Confirm the exact plugin identifier for ITF-14 and avoid its deprecated
   alias.
5. Record any platform gap in the requirements document before advertising the
   format. A required format that fails on either platform blocks that format
   from the public 1.2 support list until resolved.

Deliverables:

- barcode fixtures under `test/fixtures/barcodes/`;
- a fixture manifest containing format, exact value, generator, and expected
  platform result; and
- a confirmed 1.2 format allowlist.

### WP2 — Domain model and decoding adapter

**Depends on:** WP1.

Tasks:

1. Add `ScannedCodeFormat`, `ScanSource`, and `ScannedCode`.
2. Add the plugin-to-domain adapter and explicit format allowlist.
3. Replace `firstQrPayload` with tested extraction methods for one or many
   supported results.
4. Deduplicate results by exact format and value.
5. Preserve raw bytes only in memory; do not add them to history storage.
6. Add unit tests for every mapping, unsupported formats, empty values,
   duplicate results, ordering, leading zeroes, and raw-byte propagation.

Exit gate:

- Adapter tests cover all required formats and no scanner-page code filters
  specifically for QR Code.

### WP3 — Unified camera, gallery, and shared-image flow

**Depends on:** WP2.

Tasks:

1. Configure `MobileScannerController` with the confirmed explicit allowlist.
2. Pass `ScanSource.camera`, `.gallery`, or `.sharedImage` at the point each
   scan begins.
3. Route camera and still-image captures through the same completion method.
4. Open a single result immediately inside Dali.
5. For multiple still-image results, show a selection page or sheet containing
   the format and shortened value; open the chosen result in the same result
   view.
6. Keep camera `DetectionSpeed.noDuplicates` behavior and prevent parallel
   scan completion.
7. Update the no-result message to “No readable QR code or supported barcode
   was found in that image.”
8. Reset selection and result state correctly for **Scan again**, canceled
   gallery selection, analysis errors, and a new inbound share.

Exit gate:

- All three sources reach the same typed result state, and sharing an image
  cannot trigger a route action.

### WP4 — Result screen and safety behavior

**Depends on:** WP2; can proceed in parallel with the platform parts of WP3.

Tasks:

1. Change scanner copy from “Scan QR code” to “Scan QR code or barcode.”
2. Add a visible and accessible format label to the result screen.
3. Display the complete exact value in the existing selectable raw-content
   area and rename **Copy raw content** to **Copy contents**.
4. Rename **Save QR** and result messages to format-neutral wording such as
   **Save code**.
5. Run payload classification for presentation and optional contextual actions.
6. Calculate and display comparison codes only when
   `format == ScannedCodeFormat.qrCode`.
7. Retain the explicit confirmation dialog before browser, phone, message,
   Wi-Fi, contact, calendar, map, or app handoff.
8. Add a format-neutral barcode icon where a QR-specific icon would be
   misleading.
9. Verify screen-reader order: format, interpreted summary, full contents,
   copy/save actions, safety statement, optional external action, scan again.

Exit gate:

- A URL encoded in every supported 1D format is shown in Dali and never opens
  without an additional explicit user action.

### WP5 — History and Saved migration

**Depends on:** WP2.

Tasks:

1. Add a non-null `codeFormat` text column to `HistoryEntries`, with the stable
   QR storage key as its migration default.
2. Increase the Drift schema from version 4 to version 5 and add the column in
   the `from < 5` migration.
3. Regenerate `history_database.g.dart` with `build_runner`; do not hand-edit
   generated code.
4. Add `codeFormat` to `QrHistoryItem`, repository mappings, controller APIs,
   `onScanned`, and `onSave` callbacks.
5. Append `gallery` and `sharedImage` to `QrActivitySource`; keep `manual` and
   `camera` at their existing indexes for stored rows.
6. Change scan recording to persist the actual source rather than always
   recording camera.
7. Change recent-item lookup and save deduplication to use both payload and
   format. The same value encoded as QR and EAN-13 must remain distinguishable.
8. Generate or reconstruct QR artwork only for QR-format records. For non-QR
   history items, show the format icon and decoded value without fabricated QR
   artwork.
9. Generalize History and Saved labels from “QR” to “code” where they refer to
   both formats. Keep QR-specific language for created QR items.
10. Add a version-4-to-version-5 migration test that proves existing records
    become QR records and retain IDs, saved state, metadata, history state,
    timestamps, image bytes, and verification data.

Exit gate:

- An upgraded version-4 database opens without loss, and barcode history is
  accurately labeled by format and source.

### WP6 — Inbound-share hardening

**Depends on:** WP3.

The existing Android intent filter, iOS Share Extension, App Group, and Dart
method channel remain in place.

Tasks:

1. Rename temporary-file prefixes from `dali_shared_qr_` to a neutral prefix
   only if cleanup recognizes both old and new prefixes.
2. Enforce one image and a 25 MiB compressed-file limit before analysis;
   surface a useful error for rejected input.
3. Validate that the received path is a private temporary file owned by Dali
   before deleting it from Dart.
4. Delete temporary files after success, no result, analysis failure, and
   cancellation.
5. Sweep stale Dali inbound-share temporary files on startup so a crash or
   forced termination does not leave App Group files indefinitely.
6. Preserve cold-start and warm-app delivery semantics and ensure one share is
   consumed once.
7. Add Android tests for intent validation, copy failure, size rejection,
   replacement of a pending share, and warm delivery.
8. Replace the placeholder iOS runner test with tests around pending-path
   consumption and cleanup. Keep Share Extension logic small enough to test
   filesystem behavior independently.

Exit gate:

- The same shared image produces the same result as gallery import, and no
  terminal path intentionally retains its temporary copy.

### WP7 — Product rename

**Can proceed independently.**

Repository changes:

1. Change `MaterialApp.title` and the settings fallback name in `lib/main.dart`
   to **Dali QR**.
2. Change iOS `CFBundleDisplayName`, `CFBundleName`, and permission-purpose
   descriptions in `ios/Runner/Info.plist` to **Dali QR**. Update camera and
   photo wording to include supported barcodes.
3. Verify Android `android:label` remains **Dali QR**.
4. Verify the iOS Share Extension display name remains **Dali QR**.
5. Update user-facing tests and snapshots that intentionally assert the app
   name.
6. Update README, store-review instructions, and active product documentation.
   Preserve “Secure QR” where it names the comparison-code feature rather than
   the application.

External release tasks:

1. Rename the App Store and Google Play listing to **Dali QR**.
2. Update screenshots, descriptions, support copy, privacy-purpose copy, and
   review notes.
3. Rename the visible in-app purchase product to **Dali QR Custom** where store

Do not change:

- Android application ID `com.dalifin.qr`;
- iOS main bundle ID `com.dalifin.qr`;
- iOS Share Extension bundle ID `com.dalifin.qr.ShareExtension`;
- App Group `group.com.dalifin.qr.shared`;
- URL scheme `daliqr`;
- Drift database name `dali_qr_history`; or
- purchase product ID `dali_secure_qr_lifetime`.

Exit gate:

- A repository search finds no user-facing use of “Dali Secure QR” as the app
  name, while technical identifiers and feature-specific Secure QR references
  remain intact.

### WP8 — Versioning, regression, and release validation

**Depends on:** WP1–WP7.

Tasks:

1. Set `pubspec.yaml` to `1.2.0` with a new monotonically increasing build

2. Run formatting, static analysis, generated-code checks, and the complete
   Flutter test suite.
3. Build release candidates for both platforms.
4. Upgrade a device containing 1.1 data and an active customization entitlement
   to the 1.2 candidate; verify that neither is lost.
5. Run the physical-device format/source matrix in section 5.
6. Verify cold and warm image shares from Photos/Gallery, Files where exposed
   as an image provider, a browser, and a messaging app.
7. Confirm airplane-mode decoding and that scan/share content produces no
   network request from Dali.
8. Complete accessibility checks at large text sizes and with VoiceOver and
   TalkBack.
9. Update store metadata and submit with the 1.2 release notes.

Required repository checks:

```sh

flutter build appbundle --release
flutter build ipa --release
```

Run platform builds in correctly provisioned environments. Store signing and
submission remain release operations, not automated unit-test steps.

## 6. Automated test inventory

Add or update these test groups:

- `test/scanned_code_test.dart`: stable keys and display labels.
- `test/mobile_scanner_code_adapter_test.dart`: allowlist, mappings,
  extraction, deduplication, ordering, and malformed results.
- Replace `test/qr_image_import_test.dart` with format-neutral image-result
  tests, retaining QR regression coverage.
- Scanner widget tests: camera result, one image result, multiple result
  selection, retry, cancel, copy, save, and scan again.
- Security regression tests: non-QR result receives no comparison code and no
  decoded value auto-routes.
- Classifier regression tests: symbol format does not alter payload
  classification.
- History controller and repository tests: format/source persistence,
  payload-plus-format identity, and non-QR artwork behavior.
- Drift migration test: schema 4 fixture upgraded to schema 5.
- Inbound share Dart tests: initial and warm delivery remain exactly once.
- Android native tests and iOS native tests listed in WP6.
- App-name tests covering Flutter fallback metadata and platform plist/manifest
  values where practical.

## 7. Recommended change sequence

Use small reviewable changes in this order:

1. Fixtures and format compatibility evidence.
2. Domain model and scanner adapter with unit tests.
3. History schema version 5 and migration tests.
4. Scanner state refactor and single-result UI.
5. Still-image multi-result selection.
6. Gallery/shared source propagation and inbound-share hardening.
7. History and Saved format-neutral presentation.
8. Product rename.
9. Full regression, version bump, device matrix, and store preparation.

Do not combine the database migration and broad scanner-page refactor in one
change; keeping them separate makes data-preservation review and rollback much
safer.

## 8. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Native platforms report UPC-A/EAN-13 differently | Preserve exact values, test paired fixtures, document behavior, and avoid silent normalization |
| Enabling more formats slows or destabilizes camera detection | Use only the explicit required allowlist and test on mid-range physical devices |
| A numeric barcode is mistaken for trusted product data | Display it as an identifier only; no product claims or lookup in 1.2 |
| A URL barcode bypasses confirmation | Centralize all sources in the same inert result view and retain explicit routing confirmation |
| Secure QR is incorrectly applied to a 1D symbol | Gate comparison-code calculation on QR format in one tested method |
| Existing history loses meaning after schema change | Default migrated rows to QR, store stable strings, and test a real schema-4 fixture |
| Same value in QR and 1D history is conflated | Include format in history lookup and deduplication identity |
| A 1D scan appears as newly generated QR artwork | Restrict QR artwork reconstruction to QR records |
| Shared images remain after interruption | Delete in every terminal path and sweep stale private files at startup |
| Rename creates a new app or loses purchases | Keep all package, bundle, App Group, database, URL scheme, and product IDs unchanged |

## 9. Definition of done

Version 1.2 is ready for submission only when:

- every cell in the required validation matrix passes;
- all decoded contents open first in Dali's result view;
- no camera, gallery, or share flow automatically executes content;
- Secure QR verification remains available for QR Code and is absent for 1D
  formats;
- schema-4 upgrade tests and device upgrade tests show no user-data or
  entitlement loss;
- non-QR history correctly retains its format and source and shows no
  fabricated QR artwork;
- the application is named **Dali QR** on-device, in-app, and in both store
  listings;
- stable technical identifiers remain unchanged;
- static analysis and all automated tests pass;
- signed Android and iOS release candidates complete the physical-device
  smoke test; and
- the requirements document and release notes match the formats actually
  shipped.
